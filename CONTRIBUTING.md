# Правила работы с репозиторием

Короткие правила, которые экономят время на хакатоне. Читается один раз, соблюдается всеми.

## Перед первым коммитом

```bash
git config --global core.quotepath false
git config --global pull.rebase true
```

Первое — чтобы кириллические имена файлов читались нормально.
Второе — чтобы история не зарастала мусорными merge-коммитами.

## Ветки

Основная ветка — `Main`. Напрямую в неё не коммитим, только через Pull Request.

```
feat/<что>      новая функциональность     feat/budget-screen
fix/<что>       исправление                fix/negative-balance
content/<что>   задания, тексты, баланс    content/tasks-savings
assets/<что>    графика                    assets/pet-stage2
docs/<что>      документация               docs/architecture
```

Ветку держим короткой: одна задача — одна ветка — один PR. Ветка, живущая больше двух дней,
обязательно даст конфликты.

## Коммиты

Формат: `тип: что сделано` в повелительном наклонении, по-русски или по-английски, но
единообразно внутри своей зоны.

```
feat: экран распределения бюджета
fix: запрет отрицательного баланса при покупке
content: 3 задания по теме накоплений
assets: слои питомца, стадия 2
docs: матрица требований ТЗ
```

Не коммитим: `.jks`, `keystore.properties`, `local.properties`, содержимое `build/`.
Всё это уже в `.gitignore` — если git их видит, значит что-то настроено неправильно, спросите [@lemonke68].

## Зоны ответственности в коде

В файлы ядра (экономика, состояние питомца, хранилище, навигация) коммитит **только [@lemonke68]**.
Если вам нужно изменение в ядре — пишете [@lemonke68], а не правите сами. Это не бюрократия: расчёты
бюджета и накоплений покрываются тестами и оцениваются отдельно (ТЗ п. 8.2), случайная правка
там ломает всё разом.

Разграничение зафиксировано в [.github/CODEOWNERS](.github/CODEOWNERS).

## Pull Request

1. Создаёте PR в `Main`, заполняете шаблон.
2. Ревью делает владелец зоны из CODEOWNERS.
3. Мержим только зелёный CI.

Для графики ревью делает [@mitzzi4] — она арт-директор всего визуального потока.

## Графика

Дизайнеры складывают PNG в общую облачную папку, оттуда файлы попадают в `design/exports/`,
и уже [@zYafALL] переносит их в `app/src/main/res/` с конвертацией в WebP.

Правила именования и размеры — в [docs/assets-spec.md](docs/assets-spec.md).
Исходники ibis Paint и Procreate в репозиторий не кладём, только экспорт.

## Контент заданий

Задания, тексты и числа баланса живут в JSON в `app/src/main/assets/content/`, а не в коде.
[@vsvsokol] правит их напрямую, без участия разработчиков — это требование ТЗ п. 2.5.14:
новое задание добавляется без переработки логики приложения.

## Что проверяем перед мержем

- Приложение собирается и запускается.
- Тесты экономики проходят.
- Секретов в диффе нет.
- Новые строки интерфейса — короткие и понятные ребёнку 7–11 лет (ТЗ п. 3.6).
